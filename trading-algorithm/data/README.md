# Data

## What is checked in

`data/sample/` holds four synthetic instruments generated by
`tradelab generate` from a fixed seed. They are here so that a fresh clone can
run a backtest without hunting for a data source.

They are **not market data**. Each series was generated with a known drift,
volatility and return autocorrelation, described in
`src/tradelab/data/synthetic.py`. `SYN_TREND` has positive return
autocorrelation because that property was put there deliberately; `SYN_MEANREV`
has negative autocorrelation for the same reason; `SYN_RANDOM` is a driftless
random walk and exists as a control.

A strategy that makes money on this data has shown that the code works. It has
shown nothing about markets. Read `../README.md#what-the-results-mean` before
quoting a number from a run on it.

Regenerate them with:

```bash
tradelab generate --output data/sample
```

The output is byte-identical each time, so the checked-in files and a fresh
generation agree.

## Supplying your own data

Put one file per instrument in a directory and point a config at it:

```yaml
data:
  directory: data/raw/us_equities
  symbols: [AAPL, MSFT, SPY]      # optional; omit to load everything found
  development_end: "2019-12-31"
```

```bash
tradelab check data/raw/us_equities     # validate before trusting anything
tradelab run configs/trend_sma.yaml --data data/raw/us_equities
```

### Format

CSV (optionally gzipped) or Parquet. The symbol is taken from the file stem,
upper-cased: `aapl.csv` becomes `AAPL`.

| Column | Required | Notes |
|---|---|---|
| `ts` | yes | Parsed with `pandas.to_datetime`. `date`, `datetime`, `time` and `timestamp` are accepted as aliases. |
| `open` | yes | |
| `high` | yes | |
| `low` | yes | |
| `close` | yes | An `adj close` / `adj_close` column is renamed to `close` - see below. |
| `volume` | yes | In units of the instrument. Used by the participation cap and the volume-share slippage model. Set it to a large constant if you have no volume data, and know that you have then disabled both. |

Extra columns are dropped. Column names are lower-cased before matching.

### Use adjusted prices

The backtester compounds returns off the `close` column, so that column must be
a **total-return** series: adjusted for splits *and* dividends. If you feed it
raw closing prices:

- every dividend looks like a loss on the ex-date
- every split looks like a crash, and the data validator will flag it as an
  extreme move
- long-only results will be understated by roughly the dividend yield per year

Yahoo Finance's `Adj Close`, Norgate's total-return series and CRSP's adjusted
prices are all suitable. If your provider gives you adjusted closes but raw
open/high/low, either request adjusted OHLC or accept that the intrabar fields -
which the stop rules and the high-low range use - are on a different basis to
the close.

### Survivorship bias

If your universe is "the current members of an index", the backtest is measuring
the past performance of companies selected for having survived. This is the
single largest bias in retail equity backtesting and it is not something the
framework can detect or correct: it has no way to know which instruments are
missing. Use a point-in-time universe with delisted names included, or state
plainly that the result is subject to survivorship bias.

The engine's behaviour when an instrument stops trading - NaN close - is to
liquidate it at that bar's open rather than carry it at a stale price. That
handles a delisting *present in the data*. It cannot handle one that was never
in the file.

### What the validator checks

`tradelab check <directory>` refuses data with a missing column, a
non-monotonic or duplicated index, a non-positive price, `high < low`, or a
close outside its own bar's range. It warns about calendar gaps, single-bar
moves beyond 50%, runs of identical closes, and zero-volume bars. Warnings are
printed, not acted on: whether a 60% single-day move is a bad print or a real
event is a judgement the data owner has to make.
